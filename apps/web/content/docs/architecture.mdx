---
title: Architecture
description: The three-Worker topology, data ownership boundaries, and mail processing flows.
---

Cloudflare Inbox is a pnpm monorepo deployed as three Cloudflare Workers. The split keeps public web
traffic, authorization, and mail-domain behavior in separate trust zones.

```text
browser  ->  web Worker  ->  API Worker  ->  mail Worker
                              |                |
                              v                v
                              D1  <----------  R2
```

The arrows between Workers are Cloudflare Service Bindings. The mail Worker's `fetch` entry point is
private infrastructure; inbound email reaches its separate `email()` handler through Email Routing.

## Service responsibilities

| Component   | Owns                                                                                  | Does not own                                       |
| ----------- | ------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Web Worker  | TanStack Start UI, public docs, same-origin `/api/v1` bridge                          | D1, R2, mail credentials                           |
| API Worker  | HTTP contracts, sessions, CSRF, scopes, mailbox authorization                         | MIME rendering, public HTML pages                  |
| Mail Worker | Inbound capture, parsing, threading, forwarding, outbound delivery                    | Public browser authentication                      |
| D1          | Mailboxes, membership, threads, projections, sessions, delivery and idempotency state | Raw message or attachment bytes                    |
| R2          | Canonical raw `.eml` objects under opaque keys                                        | Browser-visible indexes or authorization decisions |

Shared packages keep the boundaries explicit: contracts define stable request and response schemas,
the database package owns SQL invariants, and mail-core contains runtime-neutral parsing, threading,
rendering, filename, and size helpers.

## Browser request flow

The browser calls `/api/v1/*` on the web origin. The web Worker preserves the method, body, query, and
authorization headers while forwarding the request through its `API` Service Binding. The API Worker
then authenticates the caller, verifies the required scope and mailbox access, validates the
contract, and calls a repository or the private mail binding.

The web Worker has no D1 or R2 binding. This prevents a UI route from bypassing authorization even if
it is implemented incorrectly.

## Inbound message flow

```text
Email Routing
  -> validate envelope and provider limits
  -> persist canonical raw message in R2
  -> parse and project safe metadata into D1
  -> associate or create a thread
  -> optionally forward to the mailbox owner
```

Durable capture happens before optional forwarding. D1 holds the searchable representation; R2
remains the source of truth for raw bytes. Attachment downloads are authorized from D1 metadata and
extracted from the corresponding raw message, so internal object keys never need to appear in a
public response.

Threading follows deterministic evidence in descending strength: an active reply alias, RFC
`In-Reply-To` and `References` identifiers, then normalized subject matching. A new inbound message
moves the thread to **Needs reply**. A successful outbound message moves it to **Waiting**.

## Outbound message flow

The API validates multipart input and reserves the idempotency key before calling the mail Worker.
The mail Worker renders a canonical MIME message, applies recipient and encoded-size limits, uses the
Email Sending binding, and records the delivery result. The API reports a safe state such as
`queued`, `sending`, `sent`, `failed`, or `unknown` without exposing provider internals.

An `unknown` result is deliberately distinct from a failure: the caller lost certainty about the
provider response and should inspect state before attempting a differently keyed send.

## Consistency and failure semantics

- D1 transactions and uniqueness constraints protect one-time tokens, projections, and idempotency.
- Raw content is written under opaque R2 keys and is never copied into structured logs.
- API responses include an opaque request ID that can be correlated across Worker hops.
- Private data responses use `Cache-Control: private, no-store`.
- Staging and production use separate Worker names, bindings, databases, buckets, secrets, routes,
  and Email Routing targets.

These boundaries make a partial failure visible and recoverable: captured mail survives forwarding
failure, archive state survives workflow changes, and an ambiguous send is not silently retried as a
new message.

## Retention flow

The mail Worker's daily scheduled handler advances durable deletion tombstones in batches of at
most 100. Raw R2 bytes are deleted first; a missing object is already a successful result. Once the
application deadline is reached, one D1 transaction removes message recipients, references,
attachments, and the message, preserves detached outbound-send history, and repairs the remaining
thread aggregates or removes an empty thread. Failed or expired claims are safely retried by a later
run. The retention handler never invokes Email Sending.
